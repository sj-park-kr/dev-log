<details class="author-question">
<summary>초보 독자 Q. 보내기를 허용하면 나쁜 사이트가 내 브라우저로 송금 요청도 보내게 할 수 있지 않나요?</summary>
<p>A. 맞아요. 그게 2편의 CSRF(다른 사이트가 내 브라우저를 시켜 요청을 보내게 하는 공격)예요. 동일 출처 정책은 응답 읽기만 막으니 이 공격은 따로 막아야 해요. 서버는 쿠키에 <code>SameSite</code> 속성을 붙이거나 CSRF 토큰(내 사이트 페이지에만 넣어 둔 무작위 값으로 다른 사이트는 읽어 갈 수 없어요)을 함께 받아서 진짜 내 페이지가 보낸 요청인지 확인해요.</p>
</details>

<details class="origin">
<summary>더 알아보기: 누가 왜 만들었을까?</summary>
<p>다른 곳의 응답을 감추는 동일 출처 정책은 넷스케이프(Netscape) 브라우저 Navigator 2.0 무렵부터 있었다고 Mozilla의 옛 보안 문서에 적혀 있어요. 페이지 안에서 스크립트가 돌기 시작하자 한 사이트가 다른 사이트의 내용을 읽어 가지 못하게 막아야 했어요.</p>
<p>웹 앱이 커지자 이번에는 다른 출처의 API를 안전하게 읽을 방법이 필요해졌어요. W3C(웹 표준 단체)에서 2005년 6월 시작한 아이디어가 2008년 "Access Control for Cross-site Requests" 초안을 거쳐 2010년 지금의 이름 Cross-Origin Resource Sharing을 얻었어요. 출처(origin)를 넘나들며(cross) 자원(resource)을 나눠 쓴다(sharing)는 뜻이에요.</p>
<p>앤 반 케스테런(Anne van Kesteren)이 편집한 이 문서는 2014년 1월 16일 W3C 권고안이 됐어요. 지금은 CORS의 정의가 WHATWG(브라우저 회사들이 함께 표준을 고치는 단체)의 Fetch 표준으로 옮겨 갔고 W3C 문서는 2020년 6월 2일 대체된 문서(Superseded Recommendation)가 됐어요.</p>
<p>참고: <a href="https://www-archive.mozilla.org/projects/security/components/same-origin">Mozilla: The Same Origin Policy</a> · <a href="https://www.w3.org/standards/history/cors/">W3C: CORS 문서 이력</a> · <a href="https://www.w3.org/TR/2014/REC-cors-20140116/">W3C CORS Recommendation (2014)</a> · <a href="https://www.w3.org/TR/2020/SPSD-cors-20200602/">W3C CORS Superseded (2020)</a> · <a href="https://fetch.spec.whatwg.org/">WHATWG Fetch Standard</a></p>
</details>

<li>허락 헤더(Access-Control-Allow-Origin)가 맞으면 읽어요</li>
<li>쿠키 등을 싣지 않는 모드면 별표(*)도 허용해요</li>
</ol>
</section>
<aside class="author-questions" aria-label="초보 독자 질문 목록">
<details class="author-question">
<summary>초보 독자 Q. Postman이나 curl로 Origin을 마음대로 적어 보내면 서버가 속지 않나요?</summary>
<p>A. Postman과 curl(브라우저 없이 서버에 요청을 보내 보는 도구)로는 Origin을 꾸밀 수 있어요. 하지만 CORS는 브라우저를 쓰는 사용자를 지키는 장치라 괜찮아요. 꾸며 보내는 사람은 남의 브라우저와 쿠키를 빌리지 못하고 자기 권한으로만 요청해요. 그래서 서버는 Origin과 상관없이 로그인과 권한 확인을 따로 해요.</p>
</details>
</aside>

</section>
<aside class="author-questions" aria-label="초보 독자 질문 목록">
<details class="author-question">
<summary>초보 독자 Q. 허락할 출처가 개발용과 배포용처럼 여러 개면 헤더에 함께 적나요?</summary>
<p>A. 아니요. <code>Access-Control-Allow-Origin</code>에는 출처 하나나 <code>*</code>만 적을 수 있어요. 그래서 서버는 목록을 두고 요청의 <code>Origin</code>이 목록에 있으면 그 값 하나를 돌려줘요. 대부분의 서버 프레임워크가 이 목록을 받는 CORS 설정을 갖고 있어요.</p>
</details>

<summary>초보 독자 Q. 남이 만든 외부 API에서 CORS 오류가 나면 어떻게 하나요?</summary>
<p>A. 남의 서버 설정은 고칠 수 없으니 먼저 API 문서에서 브라우저에서 바로 불러도 되는지 확인해요. 허락하지 않는 API라면 내 API 서버가 대신 불러서 결과를 건네주면 돼요. 서버끼리는 CORS 검사가 없고 API 키도 브라우저에 드러나지 않아요.</p>

<details class="author-question">
<summary>초보 독자 Q. 휴대폰에 설치한 앱에서도 CORS 오류가 나나요?</summary>
<p>A. 앱이 브라우저를 거치지 않고 직접 HTTP 요청을 보내면 CORS 검사는 없어요. 다만 앱 안에서 웹 페이지를 띄워 그 안의 스크립트로 요청하면 웹 페이지 규칙이 적용될 수 있어요.</p>
