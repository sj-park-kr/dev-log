<div class="intro">
<p class="q">프론트에서 내 API를 불렀을 뿐인데 브라우저는 왜 CORS 오류를 내며 답장을 막을까요?</p>
<p>네트워크 시리즈의 다섯 번째 편이에요. 바이브 코딩으로 앱을 만들면 브라우저에 화면을 그리는 프론트엔드와 1편의 API로 데이터를 주는 API 서버를 따로 띄우는 일이 많아요. 예를 들어 내 컴퓨터 자신을 가리키는 주소인 <code>localhost</code>에서 화면 파일을 브라우저에 건네주는 프론트엔드 개발 서버는 5173번 문(포트)에, API 서버는 8000번 문에 띄우고 프론트엔드에서 API를 부르면 브라우저 콘솔에 "blocked by CORS policy"라는 빨간 글씨가 자주 나와요. 서버 로그에는 요청이 왔다고 찍히기도 하는데 화면은 데이터를 받지 못하니 어디가 고장 났는지 헷갈리기 쉬워요.</p>
<p>이 글을 다 읽으면 브라우저가 다른 곳에서 온 응답을 왜 기본으로 감추는지(<b>동일 출처 정책</b>)와 무엇이 같아야 같은 곳으로 보는지(<b>출처</b>) 알 수 있어요. 응답을 보낸 서버가 읽어도 된다고 허락하는 약속인 <b>CORS</b>와 특별한 요청을 보내기 전에 먼저 묻는 <b>프리플라이트</b>도 봐요. 2편의 쿠키를 함께 보낼 때의 조건과 CORS 오류가 났을 때 고칠 곳도 살펴봐요.</p>

<details class="origin">
<summary>더 알아보기: 누가 왜 만들었을까?</summary>
<p>다른 곳의 응답을 감추는 동일 출처 정책은 넷스케이프(Netscape)의 브라우저 Navigator 2.0 무렵부터 있었다고 Mozilla의 옛 보안 문서에 적혀 있어요. 페이지 안에서 스크립트가 돌기 시작하자 한 사이트의 스크립트가 다른 사이트의 내용을 읽어 가지 못하게 막을 규칙이 필요해졌어요.</p>
<p>웹 앱이 커지면서 이번에는 다른 출처의 API를 안전하게 읽을 방법이 필요해졌어요. W3C(웹 표준을 만드는 단체)에서 2005년 6월 XML 문서 읽기를 허락하는 방법을 적은 문서로 시작한 아이디어가 2008년 "Access Control for Cross-site Requests"라는 초안을 거쳐 2010년 지금의 이름 Cross-Origin Resource Sharing을 얻었어요. 이름은 출처(origin)를 넘나들며(cross) 자원(resource)을 나눠 쓴다(sharing)는 뜻이에요.</p>
<p>앤 반 케스테런(Anne van Kesteren)이 편집한 이 문서는 2014년 1월 16일 W3C 권고안(Recommendation)이 됐어요. 지금은 CORS의 정의가 WHATWG(브라우저 회사들이 함께 표준을 고쳐 가는 단체)의 Fetch 표준으로 옮겨 갔고 W3C 문서는 2020년 6월 2일 대체된 문서(Superseded Recommendation)로 바뀌었어요.</p>
<p>참고: <a href="https://www-archive.mozilla.org/projects/security/components/same-origin">Mozilla: The Same Origin Policy</a> · <a href="https://www.w3.org/standards/history/cors/">W3C: CORS 문서 이력</a> · <a href="https://www.w3.org/TR/2014/REC-cors-20140116/">W3C CORS Recommendation (2014)</a> · <a href="https://www.w3.org/TR/2020/SPSD-cors-20200602/">W3C CORS Superseded (2020)</a> · <a href="https://fetch.spec.whatwg.org/">WHATWG Fetch Standard</a></p>

<p class="point">동일 출처 정책은 다른 출처로 요청을 보내는 일보다 스크립트가 그 응답을 읽는 일을 막아요.</p>
<p class="explain">동일 출처 정책(same-origin policy)은 한 출처에서 불러온 페이지와 스크립트가 다른 출처의 자원과 주고받는 일을 제한하는 브라우저의 기본 규칙이에요. 웹은 원래 다른 사이트의 이미지를 걸고 링크로 옮겨 다니며 자라서 보내기와 끼워 넣기까지 막으면 웹이 돌아가지 않아요. 여기서 읽는다는 건 사람이 화면으로 보는 게 아니라 스크립트가 응답 내용을 데이터로 꺼내 쓰는 일이고 브라우저는 바로 이 순간을 막아서 나쁜 가게가 은행 답장을 읽지 못하게 해요.</p>
<p>참고: <a href="https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy">MDN: Same-origin policy</a> · <a href="https://html.spec.whatwg.org/multipage/browsers.html#origin">HTML Standard: Origin</a></p>

<p class="explain">CORS(Cross-Origin Resource Sharing, 교차 출처 리소스 공유)는 서버가 HTTP 응답 헤더로 어떤 출처의 페이지가 이 응답을 읽어도 되는지 브라우저에 알려 주는 약속이에요. <code>Origin</code> 헤더는 브라우저가 직접 붙이고 페이지의 스크립트가 바꿀 수 없어서 비유에서 봉투에 적힌 보낸 가게와 같아요. 서버는 허락할 출처를 <code>Access-Control-Allow-Origin</code>에 그대로 적거나 누구나 읽어도 되는 공개 자료라면 <code>*</code>를 적어요. 서버의 응답은 브라우저까지 도착하지만 이 헤더가 없거나 값이 다르면 브라우저가 스크립트에는 건네지 않아요.</p>

<p class="point">로그인 쿠키를 함께 보내려면 스크립트가 credentials: 'include'를 주고 서버가 Access-Control-Allow-Credentials: true와 정확한 출처를 함께 보내야 해요.</p>
<p class="explain">쿠키가 붙은 응답은 그 사용자만 봐야 하는 정보일 가능성이 커서 브라우저는 누구에게나 여는 <code>*</code> 허락으로는 건네지 않아요. 그래서 로그인이 필요한 API는 허락할 출처를 목록으로 정해 두고 요청의 <code>Origin</code>이 목록에 있을 때만 그 값을 돌려줘요. 아무 <code>Origin</code>이나 그대로 되돌려 주면 나쁜 가게에도 허락 문구를 써 주는 셈이라 위험해요.</p>
<p>참고: <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS">MDN: Cross-Origin Resource Sharing (CORS)</a> · <a href="https://developer.mozilla.org/en-US/docs/Web/API/RequestInit">MDN: RequestInit</a> · <a href="https://fetch.spec.whatwg.org/#http-cors-protocol">Fetch Standard: CORS protocol</a></p>
</section>
<aside class="author-questions" aria-label="초보 독자 질문 목록">

<summary>초보 독자 Q. 허락할 출처가 개발용과 배포용처럼 여러 개면 헤더에 함께 적나요?</summary>
<p>A. 아니요. <code>Access-Control-Allow-Origin</code>에는 출처 하나나 <code>*</code>만 적을 수 있어요. 그래서 서버는 허락할 출처 목록을 코드나 설정에 두고 요청의 <code>Origin</code>이 목록에 있으면 그 값 하나를 돌려줘요. 대부분의 서버 프레임워크가 이 목록을 받는 CORS 설정을 갖고 있어요.</p>

</table>
<p class="point">CORS는 브라우저가 다른 출처의 응답을 스크립트에 건넬지 정하는 규칙이라 서버를 지켜 주지 않고 배포한 뒤 출처가 다르면 결국 API 서버의 허락으로 풀어야 해요.</p>
<p>참고: <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS">MDN: CORS</a> · <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS/Errors">MDN: CORS errors</a> · <a href="https://developer.mozilla.org/en-US/docs/Web/API/Response/type">MDN: Response.type</a> · <a href="https://vite.dev/config/server-options#server-proxy">Vite: server.proxy</a></p>
</section>
<aside class="author-questions" aria-label="초보 독자 질문 목록">
<details class="author-question">
<summary>초보 독자 Q. 남이 만든 외부 API에서 CORS 오류가 나면 어떻게 하나요?</summary>
<p>A. 남의 서버 설정은 고칠 수 없으니 먼저 그 API 문서에서 브라우저에서 바로 불러도 되는지 확인해요. 허락하지 않는 API라면 내 API 서버가 대신 불러서 결과를 건네주면 돼요. 서버끼리 주고받을 때는 브라우저가 끼지 않아서 CORS 검사가 없어요. 이렇게 하면 API 키도 브라우저에 드러나지 않아요.</p>
</details>
<details class="author-question">
<summary>초보 독자 Q. 휴대폰에 설치한 앱에서도 CORS 오류가 나나요?</summary>
<p>A. 앱이 브라우저를 거치지 않고 직접 HTTP 요청을 보내면 CORS 검사는 없어요. 다만 앱 안에서 웹 페이지를 띄워 그 안의 스크립트로 요청하면 웹 페이지 규칙이 적용될 수 있어요.</p>
</details>
