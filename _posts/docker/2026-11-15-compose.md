<div class="intro">
<p class="q">웹 서버와 DB처럼 컨테이너가 여러 개면 어떻게 한 번에 띄울까요?</p>
<p>Docker 시리즈의 4편이에요. 1편에서 앱을 밀키트 상자(이미지)에 담아 조리대(컨테이너)에서 뜯었고 2편과 3편에서 데이터를 남기는 볼륨과 컨테이너끼리 잇는 네트워크를 봤어요. 그런데 실제 앱은 웹 서버(요청을 받는 프로그램)와 DB(데이터를 보관하는 프로그램)처럼 컨테이너 여러 개가 함께 돌아서 손으로 하나씩 띄우고 이으면 금방 헷갈려요.</p>
<p>이 글을 다 읽으면 <b>compose.yaml</b>이라는 파일 한 장에 여러 컨테이너를 적고 <b>docker compose up</b>과 <b>down</b>으로 한 번에 띄우고 치우는 흐름을 알 수 있어요. 서비스끼리 이름으로 서로를 찾는 방법과 <b>depends_on</b>이 해 주지 않는 일도 함께 봐요.</p>
</div>

<p class="explain">개발자는 앱 코드 폴더에서 터미널(명령을 입력하는 창)을 열고 컨테이너마다 <code>docker run</code> 명령에 필요한 설정을 넘겨요. DB의 비밀번호는 아무 앱이나 저장된 데이터를 읽고 고치지 못하도록 접속할 사용자를 확인하는 데 필요해요. 이 설정이 개인 메모에만 있으면 동료에게 전달할 때 누락되기 쉬워요.</p>
</section>

<details class="origin">
<summary>더 알아보기: 누가 왜 만들었을까?</summary>
<p>Compose의 출발은 영국 런던의 작은 회사 Orchard가 만든 오픈 소스 도구 <b>Fig</b>예요. 벤 퍼스먼(Ben Firshman)과 아난드 프라사드(Aanand Prasad)가 Docker로 개발 환경을 빠르게 띄우려고 만들었어요. Docker, Inc.가 <b>2014년 7월</b> Orchard를 인수했어요.</p>
<p><b>2015년 2월 25일</b> 나온 1.1.0에서 Fig는 Docker Compose로 이름이 바뀌었고 명령도 <code>fig</code>에서 <code>docker-compose</code>로 바뀌었어요. 이 첫 Compose(v1)는 Python으로 만들었고 2020년에 발표한 v2는 Go로 다시 만들어 <code>docker compose</code>처럼 docker 명령 안으로 들어갔어요. v1은 2023년 7월부터 업데이트가 끊겼어요.</p>
<p>compose는 영어로 여러 부분을 모아 하나를 구성한다는 뜻이에요. 여러 컨테이너를 모아 앱 하나를 구성하는 도구라는 이름이에요.</p>

<details class="author-question">
<summary>초보 독자 Q. docker compose up을 치면 화면이 계속 붙잡혀 있나요?</summary>
<p>A. 맞아요. 기본으로는 컨테이너들의 로그가 화면에 계속 나와요. <code>Ctrl+C</code>를 누르면 멈추고 <code>docker compose up -d</code>처럼 <code>-d</code>를 붙이면 화면을 붙잡지 않고 뒤에서 실행해요.</p>
</details>
<details class="author-question">
<summary>초보 독자 Q. 코드를 고치면 web 컨테이너에 바로 반영되나요?</summary>
<p>A. 이미지에 복사해 둔 코드는 자동으로 바뀌지 않아요. <code>docker compose up --build</code>로 이미지를 다시 빌드하면 반영돼요.</p>
<p>빌드 없이 바로 반영하고 싶다면 2편의 바인드 마운트를 compose.yaml의 web 서비스 volumes에 적어 코드 폴더를 컨테이너에 연결해요.</p>
</details>
<details class="author-question">
<summary>초보 독자 Q. Compose는 따로 설치해야 하나요?</summary>
<p>A. Docker Desktop에는 처음부터 들어 있어요. 리눅스 서버에서는 Docker Engine과 별도로 Compose 플러그인을 설치해야 할 수 있어요. 설치되어 있는지는 <code>docker compose version</code>으로 확인해요.</p>
</details>
<details class="author-question">
<summary>초보 독자 Q. Ctrl+C로 멈추는 것과 down은 뭐가 다른가요?</summary>
<p>A. 화면에 붙여 실행한 <code>docker compose up</code>에서 Ctrl+C를 누르면 실행만 멈추고 컨테이너와 네트워크는 남아요. down은 멈춘 뒤 그것들까지 지우며 기본으로 볼륨은 남겨요.</p>
</details>

<pre><code># 앞 예의 services 안 web과 db에 각각 덧붙일 부분
services:
  web:
    depends_on:
      db:
        condition: service_healthy
  db:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10</code></pre>
<p>CMD-SHELL은 명령 해석기(셸)로 검사 명령을 실행하라는 뜻이에요. pg_isready는 접속 가능 여부를 묻고 <code>-U postgres</code>는 postgres 사용자로 확인한다는 뜻이에요.</p>
<p class="point">depends_on에 서비스 이름만 적으면 DB 컨테이너가 켜진 뒤 웹을 시작하지만 DB가 요청을 받을 준비까지 기다리지는 않아요.</p>
<p class="explain">DB는 켜진 뒤에도 초기 준비를 하므로 web이 너무 일찍 접속하면 실패할 수 있어요. 앱이 재시도 없이 오류로 종료하면 기본으로 멈추며 restart(종료 뒤 다시 실행하는 규칙)를 on-failure로 정하면 오류 종료 후 다시 실행해요. healthcheck는 비유의 맛보기처럼 준비 여부를 주기적으로 검사하며 예시 코드는 앞 주문서의 web과 db에 대기 조건과 검사를 덧붙이는 부분이에요. 예시처럼 service_healthy를 기다리는데 DB 검사가 retries 횟수만큼 연속 실패해 검사 실패 상태(unhealthy)가 되면 web은 시작되지 않고 up이 오류를 알려요.</p>
