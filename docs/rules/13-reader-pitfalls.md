## 13. 독자가 실제로 막힌 이유

작성자가 자기 글을 읽다가 "이해가 안 돼"라고 한 기록에서 뽑은 규칙이다. 글 작성자와 검토 서브에이전트가 함께 쓴다. 근거는 2026-11-15부터 11-26까지 이 PC에 남은 Claude·Codex 세션이다. Claude는 직접 입력한 짧은 발언(600자 이하)을 모두 읽었고 Codex는 검색어에 걸린 발언만 읽었다. 인용의 오타는 그대로 둔다. "왜"는 인용과 당시 글을 보고 **추정한 원인**이다.

다른 문서와 부딪히면, 아래 유형에 실제로 걸린 페이지에서는 이 문서가 우선한다.

### 검토할 때 확인할 것

페이지마다 아래를 하나씩 확인하고, 걸리면 **유형 번호, 페이지 제목, 막히는 글자, 고칠 방향**을 보고한다.

#### P1. 비유가 실물을 가린다
- 실제 반응: "빈 볼륨이랑 빈집 서랍은 각각 뭘 뜻하는 거야?", "비유하니까 더 보기 힘들어", "송파, 판교 이런게 뭐야", "갑자기 DB가 뭔 소린지"
- 왜: 독자가 비유를 실제 이름으로 번역해야 했다. "빈 집 서랍"은 "빈집의 서랍"으로도 읽혔다. 비유 이름과 실제 이름을 나란히 더 적었더니 글자만 늘어 더 어려워졌다.
- 확인: 비유 낱말에 꾸미는 말(빈, 새, 우리)을 붙였을 때 다르게 읽히지 않는가. 독자가 **실제로 골라 써야 하는 두 가지**를 비교하는 페이지라면 비유 없이 실제 이름으로 읽히는가.
- 고치기: 실제로 골라 써야 하는 둘은 실제 이름으로 비교한다. 차이가 명령이나 설정값에 있으면 **달라지는 부분만 위아래로 나란히** 보여 준다(예: `-v my-vol:/app`과 `-v ./empty:/app`). 이 비교는 "명령어 나열 금지"의 예외다. 설치 절차를 늘어놓는 데는 쓰지 않는다.

#### P2. 비슷한 둘의 관계가 없다
- 실제 반응: "볼륨의 종류를 말하는 거야?", "결국은 두 개 다 같은 볼륨 아닌가?", "컴팩션이랑 retain 겹치는거 아니야?", "커밋이랑 처리랑 무슨 소리야?", "정적, 동적 차이를 모르겠어"
- 왜: 각각은 설명했지만 같은 종류인지 다른 것인지, 겹치는지, 함께 쓰는지를 말하지 않았다.
- 확인: 이름이 비슷하거나 나란히 놓인 둘이 있으면 "둘은 어떤 사이인가"와 "무엇 하나가 달라서 갈리는가"의 답이 페이지에 있는가.

#### P3. 누가 언제 하는지 없다
- 실제 반응: "이걸 누가 설ㅈ어하는거야?", "누가 요청을 한다는 거야?", "이걸 언제 어디에 적으라는 거야", "컨슈머 입장에서 쓴 거야?", "5초 간격인데 왜 달라고 해야 오토 커밋을 해?"
- 왜: 문장에서 주체나 시점이 빠졌다.
- 확인: 동작마다 누가(사람·앱·도구), 언제(어떤 일이 생기면), 무엇을, 어디에 하는지 답할 수 있는가. 사람이 설정하는 것과 도구가 알아서 하는 것이 구분되는가.

#### P4. 갑자기 나온 말
- 실제 반응: "자동 삭제가 뭘 말하는 거야?", "층이 뭘 말하는거야?", "끈금없이 툼스톤 나오니까 이해가 되지 않잔아", "세그먼트가 이해가 안되는게", "동네가 없다는 게 뭐야? 그 값이 없다는 거야?", "쿼럼이란게 뭐야?"
- 왜: 제목이나 그림 이름표의 말이 무엇인지 앞에서 알려 주지 않았다. "자동 삭제"처럼 쉬운 말도 **무엇이** 삭제되고 **무엇을 해야** 그렇게 되는지 없으면 막힌다. 우리가 새로 만든 우리말("쓰기 층", "자동 삭제 뒤 보관")도 마찬가지다.
- 확인: 제목과 그림 이름표만 읽고 각 낱말이 가리키는 대상을 말할 수 있는가. 줄인 말에 대상이 빠지지 않았는가.

#### P5. 왜 필요한지, 언제 쓰는지 없다
- 실제 반응: "7일 이전은 모두 삭제하면 되잖아. 왜 굳이 칸으로 나누는거야?", "제일 마지막꺼만 읽으면 되는거 아니야?", "오토 커밋은 보통 언제 써?", "이런 건 보통 언제 하는 거야?", "4번 개념이 왜 나오는 거야?"
- 왜: 동작만 있고, 독자가 먼저 떠올리는 **더 단순한 방법이 왜 안 되는지**나 쓰는 상황이 없었다.
- 확인: "그냥 이렇게 하면 안 돼?"가 떠오르는 곳에 답이 있는가. 앞 페이지와 이어지지 않는 개념이 튀어나오지 않는가.

#### P6. 그림이 차이를 보여 주지 않는다
- 실제 반응: "이 그림 너무 똑같아. 이게 설명이 다른데", "012, 012가 다 같잖아", "이게 2-1에 적은 거랑 차이가 없잖아", "2-1처럼 표현해 주는 게 더 편할 것 같아", "주문 서비스랑 리더… 카드 안에 또 다시 넣어서 구분"
- 왜: 글은 다르다고 하는데 그림은 같은 모양이거나, 비교 기준이 달랐다.
- 확인: 글자를 가려도 달라진 곳이 보이는가. 앞 페이지 그림과 구별되는가. 그림의 중심이 제목이 말하는 것인가.

#### P7. 그림이 실제 동작과 어긋난다
- 실제 반응: "다 꺼졌는데 주문이 계속 넣네", "점의 이동이 2번째 선에서 끝나네?", "주문 선반을 보다는 주문 선반의 칸에 그 제품을 바라봐야 될 것 같은데", "읽은 서비스가 중간에 하나 더 있어야 되는 거 아니야?", "누가 요청을 한다는 거야?"(제목과 내용 불일치)
- 확인: 화살표의 출발과 도착이 실제 주체와 대상인가. 중간 단계가 빠지지 않았는가. 움직임이 설명한 조건(꺼짐, 순서)을 지키는가.

#### P8. 반복하거나 겹친다
- 실제 반응: "위에서 굳이 다 설명하는데 아래에 이렇게 더 있어야 되나", "이거 중복 아니야?", "3-1에 있으니까 굳이 이걸 넣어야 되나?"
- 확인: 같은 말을 두 번 하지 않는가. 접이식 질문과 본문의 숫자·조건이 서로 다르게 읽히지 않는가.

#### P9. 압축하거나 위계가 없다
- 실제 반응: "너무 축약되어 있다", "뭐에 대한 설명인 건지 모르잖아", "글을 읽었을 때 이해가 되지 않았어"
- 확인: 제목이 무엇에 대한 이야기인지 말하는가. 한 줄에 조건을 여러 개 눌러 담지 않았는가. 부족하면 글자를 늘리지 말고 페이지나 그림을 나눈다.

#### P10. 화면에서 읽히지 않는다
- 실제 반응: "글자가 일자로 안 보이는데?"(번호 줄의 flex 때문에 `<code>`가 따로 칸이 됨), "선 사이에 글자들이랑 겹쳐", "다크모드… 잘 안보여", "화살표랑 … 크로스되네"
- 확인: **소스만 읽어서는 알 수 없다.** 화면을 열어 번호 줄의 줄바꿈, 그림의 겹침, 라이트·다크 대비를 본다. 서브에이전트는 파일을 읽어 위험한 곳(긴 이름표, 교차하는 선)을 짚고, 화면을 보지 않았으면 "미확인"이라고 적는다.

### 이해가 안 된다는 말을 들었을 때

1. **대화에서 먼저 설명한다.** 어느 낱말에서 막혔는지 짚는다. 글은 바로 고치지 않는다. 사용자가 수정까지 요청하면 고친다.
2. **통한 설명을 그대로 글에 옮긴다.** 실제 반응: "아 이제 이해가 되네 이렇게 설명해준대로 글 작성해줘", "그렇게 설명해야 더 이해가 잘 될 것 같아". 통한 설명에 없던 비유·라벨·정보를 옮기면서 덧붙이지 않는다.
3. **같은 원인이 다른 페이지에도 있는지 찾는다.** 요청 범위 밖은 고치지 말고 알려 준다.
4. **이 문서를 갱신한다.** 같은 작업 안에서 한다. 기존 유형이면 새 반응이 확인 질문을 바꿀 때만 인용이나 확인 항목을 고친다. 새 유형이면 `실제 반응 → 왜 → 확인`으로 추가한다. 한 유형의 인용은 6개를 넘기지 않는다. 갱신했는지 완료 보고에 한 줄로 적는다.
