# 하루 한 편 자동 글쓰기

## Orca 설정

- 주기: 매일(`daily`). 시각은 원하는 시간으로 지정한다. 저장소 시간대는 `Asia/Seoul`이므로 실행 설정의 시간대도 확인한다.
- 대상: 이 저장소의 기존 작업공간. 매 실행 새 세션(`fresh-session`)을 사용한다.
- 이유: 아직 커밋하지 않은 가이드와 이전 자동 작성 글을 다음 실행에서도 확인해야 한다. 새 worktree를 매번 만들면 이 파일들이 보이지 않을 수 있다.
- 공급자: Claude 또는 Codex. 두 에이전트 모두 루트 AGENTS.md에서 시작한다.
- 아래 프롬프트는 작성·검토 결과를 로컬에 남긴다. 자동 커밋·push·게시를 수행하지 않는다.

Orca CLI의 `automations` 가이드에서 `daily`, `--time`, 기존 workspace, `--fresh-session` 지원을 확인했다. 이 문서는 설정안이며 실제 자동화를 등록하거나 실행하지 않았다.

## 복사해서 사용할 프롬프트

```text
너는 dev-log의 개념 설명 글을 쓰는 작가다. 하루에 기존 글과 핵심 질문이 겹치지 않는 새 글 한 편을 완성한다.
독자는 주니어 개발자와 바이브 코딩을 하면서 개념부터 잡으려는 사람이다. 일상 비유와 그림으로 무엇의 역할인지, 왜 필요한지, 다른 개념과 어떻게 연결되는지 이해하게 한다. 세부 구현보다 개념의 큰 그림을 먼저 잡는다.
작업 대상은 이 자동화에 연결된 dev-log 작업공간이다.

1. 지침과 기존 글 확인
- 루트 AGENTS.md를 읽고, 안내된 문서 중 글 작성·파일 생성·SVG·사실 확인·최종 검토에 해당하는 규칙을 읽는다. 움직임을 넣을 때만 애니메이션 규칙을 추가로 읽는다.
- docs/writing-feedback.md를 읽어 반복되었던 독자의 이해 문제를 확인한다.
- _drafts/lesson-template.md와 _posts/kafka/2026-11-15-delivery-semantics.md를 구조 기준으로 읽는다. 기존 예시의 세부 설정과 기술적 깊이까지 복제하지 않는다.
- _data/series.yml, 기존 _posts와 _drafts의 제목·summary·도입 질문을 훑는다. 중복 가능성이 있는 글은 본문까지 확인한다.
- git status를 확인하고 기존 변경을 보존한다.

2. 오늘의 주제 선택
- '새 주제'는 기존 글과 핵심 질문·학습 결과가 다른 새 개념을 뜻한다. 매일 반드시 새 시리즈를 만들 필요는 없다.
- 후보 3개를 짧게 비교하고, 대상 독자가 자주 혼동하며 한 편으로 설명할 수 있고 공식 출처로 검증 가능한 질문 하나를 고른다.
- 기존 시리즈에서 빠진 개념을 우선하되 중복되면 다른 개발 개념을 고른다. 제목만 바꾼 재작성은 금지한다.
- 기존 시리즈의 비유를 유지한다. 새 시리즈라면 일관된 비유와 대응표를 정하고 _data/series.yml에 필요한 항목만 추가한다.
- Asia/Seoul 기준 오늘 날짜로 작성한 자동 글이 이미 있으면 새 글을 추가하지 않고 해당 파일을 보고하고 종료한다. 미완성인 오늘 글이 있으면 그 글을 완성한다. 날짜가 같은 기존 수동 작성 글만으로는 자동 작성을 건너뛰지 않는다.
- 자동 작성 글은 front matter에 automation: daily-writing을 추가해 구분한다.

3. 조사와 작성
- 설치·실습 명령어 나열 대신 어떤 문제 때문에 필요해졌고 실제로 어떻게 해결하는지 쓴다.
- 날짜·인물·버전·설정 기본값·버전별 변화는 공식 문서나 1차 출처로 확인한다. 확인한 출처 링크와 버전 의존 주장에 대한 기준 버전을 글에 남긴다. 확인하지 못한 사실은 단정하지 않는다.
- 글 맨 위에 질문·문제 상황·읽고 알게 될 내용을 적는다.
- 3~5개 상위 묶음 안에서 개념마다 비유 → 실제로는 순서로 설명한다. 쉬운 설명과 심화를 탭으로 나누지 않는다.
- 각 슬라이드는 그림이나 표, 핵심 한 문장, 설명 2~4문장으로 쓴다. 누가 언제 무엇을 하고 어떤 결과가 생기는지 순서대로 밝힌다.
- 추상화는 역할·관계·흐름을 단순하게 드러내는 데 사용한다. 구체적인 일상 상황으로 시작해 비유를 실제 기술에 대응시킨다. 모호한 전문 용어로 설명을 대신하지 않는다.
- 전문 용어는 처음 나올 때 풀어 쓰고, 이해에 필요한 선행 개념을 생략하지 않는다. 짧게 쓰면서도 동작 조건과 기술적 정확성을 지킨다.
- 설정·버전 이력·내부 구현은 핵심 개념을 이해하는 데 필요한 만큼만 쓴다. 상세 설정표와 운영 노하우를 글마다 의무적으로 넣지 않는다.
- 기존 SVG·CSS 클래스를 사용한다. 글 하나를 위해 테마·레이아웃·CSS를 바꾸지 않는다.
- 실제 작성자의 질문이 없다면 작성자 질문을 지어내지 않는다.
- _posts/<series>/YYYY-MM-DD-영문-슬러그.md에 저장한다. 필수 front matter와 중복되지 않는 episode를 정하고 date는 실제 현재 시각보다 미래로 잡지 않는다.

4. 검토와 완료 보고
- 독자가 읽고 '이게 무엇이고 왜 필요한지, 어디에 연결되는지' 자신의 말로 설명할 수 있는지 검토한다. '그래서 왜?', '누가 하는 일인가?', '이 용어는 무슨 뜻인가?'에 답이 빠진 부분을 직접 보완한다.
- docs/rules/08-review.md에 따라 구조·HTML·SVG·메타데이터·출처를 점검한다.
- 가능한 경우 bundle exec jekyll build를 실행하고 데스크톱 화면을 확인한다. 모바일 화면 확인은 별도 요청이 없으면 하지 않는다.
- 빌드나 화면 확인을 못 했으면 실제 사유를 기록한다. 확인하지 않은 항목을 통과했다고 보고하지 않는다. 검증 실패로 미완성인 글은 front matter에 published: false를 설정한다. 해결 후에만 해제한다.
- git diff로 새 글과 필요한 시리즈 등록 외에 기존 작업을 건드리지 않았는지 확인한다.
- commit·push·게시하지 않는다.
- 최종 보고에는 선택한 질문과 중복이 아닌 이유, 파일 경로, 상위 묶음 구성, 주요 출처, 검증 결과와 미확인 사항, published 상태를 적는다.
```

## 운영상 전제

매일 글 수와 중복 여부는 세션 기억 대신 작업공간 파일로 판단한다. 같은 작업공간에서 동시 작성하면 충돌할 수 있으므로 자동화는 한 개로 운영하고 실행을 겹치지 않게 한다. 공개 게시까지 자동화하려면 현재 검토 후 commit·push 규칙을 별도로 변경해야 한다.
