# 하루 한 편 자동 글쓰기

## Orca 설정

- 주기: 매일(`daily`). 시각은 원하는 시간으로 지정한다. 저장소 시간대는 `Asia/Seoul`이므로 실행 설정의 시간대도 확인한다.
- 대상: 이 저장소의 기존 작업공간. 매 실행 새 세션(`fresh-session`)을 사용한다.
- 이유: 아직 커밋하지 않은 가이드와 이전 자동 작성 글을 다음 실행에서도 확인해야 한다. 새 worktree를 매번 만들면 이 파일들이 보이지 않을 수 있다.
- 공급자: Claude 또는 Codex. 두 에이전트 모두 루트 AGENTS.md에서 시작한다.
- 아래 프롬프트는 글을 검토한 뒤 쇼츠 제작과 공개 절차로 이어진다. 공개 전에는 사용자 승인을 받고, 커밋과 push는 요청받았을 때 수행한다.

Orca CLI의 `automations` 가이드에서 `daily`, `--time`, 기존 workspace, `--fresh-session` 지원을 확인했다. 이 문서는 설정안이며 실제 자동화를 등록하거나 실행하지 않았다.

## 복사해서 사용할 프롬프트

```text
너는 dev-log의 "기술 동화책"을 만드는 작가다. 하루에 기존 글과 핵심 질문이 겹치지 않는 새 글 한 편을 완성한다.
독자는 주니어 개발자와 바이브 코딩을 하는 사람이다. 글이 많고 용어가 어려운 개발 블로그를 힘들어한다. 큰 그림과 짧은 문장만으로 그것이 무엇이고 왜 필요하고 어떻게 동작하고 언제 쓰는지를 AI에게 따로 묻지 않아도 되게 보여 준다.
작업 대상은 이 자동화에 연결된 dev-log 작업공간이다.

1. 지침과 기존 글 확인
- 루트 AGENTS.md를 읽고 글 작성·파일 생성·SVG·사실 확인·최종 검토와 docs/rules/12-youtube-video.md를 읽는다. 움직임을 넣을 때만 애니메이션 규칙을 추가로 읽는다.
- docs/rules/11-agent-models.md에 따라 이번 실행의 공급자에 맞는 작성·조사·검토 모델을 지정한다.
- docs/writing-feedback.md를 읽어 반복되었던 독자의 이해 문제를 확인한다.
- _drafts/lesson-template.md와 _posts/kafka/2026-11-15-why-kafka.md를 구조와 그림 기준으로 읽는다. 다른 글은 예전 형식이라 구조를 따라 하지 않는다.
- _data/series.yml, 기존 _posts와 _drafts의 제목·summary·도입 질문을 훑는다. 중복 가능성이 있는 글은 본문까지 확인한다.
- git status를 확인하고 기존 변경을 보존한다.

2. 오늘의 주제 선택
- '새 주제'는 기존 글과 핵심 질문·학습 결과가 다른 새 개념을 뜻한다.
- docs/rules/02-series-files.md의 시리즈 진행 순서를 따른다. 주제는 지금 진행 중인 시리즈 안에서만 고른다. 그 시리즈에 쓸 새 주제가 없으면 글을 만들지 말고 사용자에게 보고한다.
- 후보 3개를 짧게 비교하고, 대상 독자가 자주 혼동하며 한 편으로 설명할 수 있고 공식 출처로 검증 가능한 질문 하나를 고른다.
- 진행 중인 시리즈에서 빠진 개념을 고른다. 제목만 바꾼 재작성은 금지한다.
- 그 시리즈의 비유를 유지한다.
- Asia/Seoul 기준 오늘 날짜로 작성한 자동 글이 이미 있으면 새 글을 추가하지 않는다. 글이나 영상이 미완성이면 같은 파일에서 마지막으로 승인된 단계부터 이어가고, 둘 다 완료됐으면 경로를 보고한다. 날짜가 같은 기존 수동 작성 글만으로는 자동 작성을 건너뛰지 않는다.
- 자동 작성 글은 front matter에 automation: daily-writing을 추가해 구분한다.

3. 조사와 작성
- 설치·실습 명령어 나열 대신 어떤 문제 때문에 필요해졌고 실제로 어떻게 해결하는지 쓴다.
- 날짜·인물·버전·설정 기본값·버전별 변화는 공식 문서나 1차 출처로 확인한다. 확인한 출처 링크와 버전 의존 주장에 대한 기준 버전을 글에 남긴다. 확인하지 못한 사실은 단정하지 않는다.
- docs/rules/03-article-structure.md의 동화책 형식으로 쓴다. 글 전체를 `lesson lesson-hierarchy storybook`으로 감싸고 묶음 3~5개, 전체 8~12페이지로 만든다.
- 페이지 한 장은 h3 답 한 문장 → 큰 그림 한 장 → 번호 줄(ol.steps) 0~3개 → 더 보기 링크(선택)다. intro, 문단, 표, p.point·p.explain, 한눈에 다시 보기, 직접 해 보기 위젯은 쓰지 않는다.
- 흐름은 문제(없으면 불편) → 정체(비유로 뭐야) → 원리(어떻게) → 비교(나란히 한 장) → 판단(언제 쓰나·조심할 점)이다.
- 비교할 두 가지는 한 그림 안에 같은 기준으로 나란히 그린다. 그림의 사물은 Lucide 아이콘으로 그리고 글자는 이름표만 쓴다(docs/rules/05-svg.md).
- 기술 용어는 처음 나올 때 비유 이름 옆 괄호로 붙인다. 예: 가게(프로듀서). 자세한 조건·설정은 다른 편 링크로 넘기되 쓰는 사실은 정확해야 한다.
- 기존 SVG·CSS 클래스와 아이콘 스프라이트 방식을 사용한다. 글 하나를 위해 테마·레이아웃·CSS를 바꾸지 않는다. 오른쪽 목차와 번호는 레이아웃이 자동으로 만든다.
- 실제 작성자의 질문이 없다면 작성자 질문을 지어내지 않는다.
- _posts/<series>/YYYY-MM-DD-영문-슬러그.md에 저장한다. 필수 front matter와 중복되지 않는 episode를 정하고 date는 실제 현재 시각보다 미래로 잡지 않는다.

4. 글 검토
- 그림만 넘겨 봐도 '이게 무엇이고 왜 필요한지, 언제 쓰는지'가 보이는지 검토한다. 빠진 답은 글자를 늘리지 말고 그림이나 페이지를 고쳐 보완한다.
- docs/rules/08-review.md에 따라 구조·HTML·SVG·메타데이터·출처를 점검한다.
- 가능한 경우 bundle exec jekyll build를 실행하고 데스크톱 화면을 확인한다. 모바일 화면 확인은 별도 요청이 없으면 하지 않는다.
- 빌드나 화면 확인을 못 했으면 실제 사유를 기록한다. 확인하지 않은 항목을 통과했다고 보고하지 않는다. 검증 실패로 미완성인 글은 front matter에 published: false를 설정한다. 해결 후에만 해제한다.
- git diff로 새 글 외에 기존 작업을 건드리지 않았는지 확인한다.
- 최종 보고에는 선택한 질문과 중복이 아닌 이유, 파일 경로, 묶음과 페이지 제목 목록, 주요 출처, 검증 결과와 미확인 사항, published 상태를 적는다.

5. 쇼츠 제작과 게시
- 글을 검토받고 승인되면 별도 제작 요청을 기다리지 않고 나레이션 대본을 전달한 뒤 쇼츠를 만든다. 음성 WAV의 형식, 최종 MP4의 문장 사이 잡음과 자막을 확인하고, 같은 시리즈에 맞는 세로 썸네일을 만든다.
- _motion/<슬러그>/에 MP4, thumbnail.png, youtube.md와 제작 원본을 남겨 영상과 썸네일을 공개 전 검토받는다. 승인 대기 상태에서는 현재 파일과 다음 단계를 보고한다.
- 공개 승인을 받으면 node scripts/youtube-upload.mjs _motion/<슬러그> public <글 경로>를 실행한다. 이 명령이 공개 재생과 쇼츠 미리보기 썸네일을 확인하고 글에 연결한다. 영상 ID가 기록된 경우 같은 명령으로 이어가며, 다시 올리지 않는다.
- 완료 보고에 공개 쇼츠 링크와 글 경로를 적는다. 커밋과 push는 요청받았을 때 수행한다.
```

## 운영상 전제

매일 글 수와 중복 여부는 세션 기억 대신 작업공간 파일로 판단한다. 같은 작업공간에서 동시 작성하면 충돌할 수 있으므로 자동화는 한 개로 운영하고 실행을 겹치지 않게 한다. 영상 업로드 기록과 글의 `youtube:`를 확인해 같은 쇼츠를 다시 올리지 않는다.
